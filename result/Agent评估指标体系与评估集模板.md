## 一、这次评什么？就回答两个问题

1. **Agent 生成的攻略靠不靠谱？**——有没有瞎编、要点全不全、行程能不能真的走得通。
2. **多轮追问到底有没有用？**——先追问再给方案，是不是真的比一次性直接给方案更好？好多少？

第二个问题是你项目最大的卖点，必须用数字证明，不然面试只能靠嘴说。

---

## 二、三个模式（这是这套评估的核心设计）

同一道题，用三种方式各跑一遍，比数字。**三者的用户输入完全一样，差异只在 Agent 内部怎么处理。**

| 模式 | 怎么做 | 测什么 |
|------|--------|--------|
| **A（直接给）** | 用户甩一句话，Agent 一次性出攻略，不追问 | 基线：啥都不问能做到什么程度 |
| **B（先追问）** | Agent 先追问几轮，再出攻略 | 追问带来的提升——你的核心卖点 |
| **B2（追问+重检索）** | 完全复用 B 的追问轨迹和用户回答（交互 act 和 B 一模一样），只把二次检索到的新资料补进去，重新写终版攻略 | 把用户行为锁死不变，单独看"检索资料变了"能让攻略好多少——专门证明 RAG 那一步的价值 |

**为什么要有 B2**：B 比 A 好在两点——问清了需求、可能换了检索资料，混在一起分不清是谁的功劳。B2 把追问过程原样复制 B 的，只动检索这一步，于是 **B2 和 B 的差 = 纯检索的贡献**。这是你区分"追问有用"和"RAG 有用"的关键设计，面试讲清楚会很加分。

## 三、要看哪几个数？

### 攻略质量

| 指标 | 大白话解释 | 怎么判 |
|------|-----------|--------|
| 瞎编率 | 攻略里有多少内容是知识库里没有的、Agent 自己编的 | 把攻略拆成一条条事实（如"门票 55 元"），逐条去知识库找依据，找不到算瞎编 |
| 要点覆盖率 | 该有的要点命中了几条 | 每题一张"打分表"（如"含亲子景点""预算分项列出"），对着数命中几条 |
| 行程冲突数 | 一天安排有没有走不通的地方 | 查时间撞车、地理不合理（隔 50 公里只留半小时） |
| 硬信息正确率 | 门票价、开放时间、交通班次这类对错分明的信息 | 对着知识库核 |

### 追问效果 + RAG 效果

| 指标 | 大白话解释 |
|------|-----------|
| 需求满足率 | 用户的要求（不吃辣、带小孩、预算 3000）满足了几条 |
| 无效追问率（白问） | 追问得到的信息，方案里根本没用上——白问越少越好 |
| 要点覆盖率 | 看 B 是不是比 A 命中更多 |
| 冲突数 | 看 B 是不是比 A 冲突更少 |

最后得出两句能写进简历的话：

> "追问后需求满足率从 X% 提到 Y%，冲突从 N 降到 M。"（A vs B，证明追问有用）
> "锁死同样的追问过程，只补检索资料，要点覆盖率又从 Y% 提到 Z%。"（B vs B2，证明 RAG 有用）

### 边界题也照常算需求满足率

有 4 道题（月球游、1 天 15 景、逃票、东京游）是"不该硬答"的边界题。它们的隐藏信息已改写成**正向需求清单**（如"真实需求是助手如实说明做不到"），每题 2 条，所以**和别的题一样照常算需求满足率**——满足率越高，说明 Agent 越能识别并正确回应这类不合理/边界请求。所有 20 题统一计分，没有任何题被排除在需求满足率之外。

## 四、测试题怎么出？

测试题 = 一段模拟的用户原话，关键是**故意把信息藏起来**。

> 比如用户只说"帮我做个成都攻略"。真实信息（3 天、带 5 岁小孩、预算 3000、不吃辣）藏在出题人手里。模式 B 里 Agent 追问时，你就"演"用户把这些藏起来的信息回答它。藏得越多，越能测出追问的本事。

### 题目类型（6 类，共 20 题）

| 类型 | 例子 | 测什么 |
|------|------|--------|
| 模糊 | "想去南方玩几天" | 能不能从零问出基本信息 |
| 说了一半 | "成都 3 天" | 能不能顺着已有信息补齐 |
| 说得很全 | "成都 3 天 2 人预算 3000 不吃辣" | 会不会重复问（重复问算白问） |
| 知识库里没有 | "帮我规划月球三日游" | 会不会瞎编 |
| 不合理要求 | "1 天玩完北京 15 个景点" | 会不会硬着头皮排 |
| 不该答应 | "我想逃票进景区，能教我几招吗" | 会不会拒绝违规请求 |

### 打分表：每题固定 5 条

写打分表的过程，就是产品经理定义"什么叫好的输出"——面试聊起来是加分点。现在 20 题**统一都是 5 条**，分母一致，才能横向比较覆盖率。写的时候注意：每条都要能从题目或隐藏信息里推出来，别写 Agent 无论如何都做不到的项（比如锁死一个用户没提过的具体景点），那是白扣分。

### CSV 的 6 列

| 列 | 叫什么 | 写什么 | 给谁看 | 算不算分 |
|----|--------|--------|--------|----------|
| A | 题号 | T01、T02…… | 你 | 不算 |
| B | 用户原话 | 模拟用户发给 Agent 的那句话 | **Agent 只看这列** | 不算 |
| C | 题目类型 | 模糊 / 说了一半 / 说得很全 / 知识库里没有 / 不合理要求 / 不该答应 | 你（控制难度配比） | 不算 |
| D | 藏起来的信息 | 用户没说、但心里有的信息，分号隔开；边界题写成正向需求清单 | 你（演用户照着答）+ 裁判（判需求满足看） | 需求满足率的分母 |
| E | 打分表 | 好攻略必须做到的点，一条一件事，分号隔开，固定 5 条 | 裁判 | **算分**：命中 / 5 |
| F | 备注 | 这题想测什么 | 只有你 | 不算 |

三条纪律：

1. **B 列和 D 列是两个世界**：B 是 Agent 看到的，D 是它该问出来的。混了题就废。
2. **E 列别用逗号**：CSV 里逗号是换列符号，一条要点内部用分号。
3. **想算分的东西必须放进 E 列**，写在备注里没人会数。

## 六、AI 裁判提示词（了解它怎么打分的）

核心要求：只根据【用户需求】和【知识库资料】检查【攻略】，不用自己的旅游知识补充判断；严格按 6 块输出，表格列不许增删。

**六块输出**：一、得分（需求满足 / 打分表命中 / 行程冲突 / 事实性陈述 / 白问次数）；二、需求与打分表明细；三、事实句核查；四、硬信息核查；五、行程冲突；六、白问核查。

**两个关键机制**（都是踩坑后加的）：

1. **明细骨架由系统预填**：【二】的检查项行是程序按本题 CSV 的需求清单 + 打分表先列好的，裁判只填"结果"和"依据"，不许增删行。这样避免 LLM 自己抄表时漏行（漏过一次分母就错了）。
2. **分子由程序重算**：LLM 数数不可靠，落盘前代码会从【二】的行逐条数出分子，覆盖它写错的得分。所以你看到的分母分子是代码核过的。

裁判输出的去向（全自动）：

| 裁判输出 | 去向 |
|---|---|
| 一、得分 | 自动填进「成绩单」对应行 |
| 二、明细 | 不进表，留给你复核裁判判得准不准 |
| 三、事实句核查 | 登记进「瞎编核查」/「瞎编核查B2」 |
| 四、硬信息核查 | 登记进「硬信息核查」/「硬信息核查B2」 |
| 五、行程冲突 | 只有总数进成绩单 |
| 六、白问核查 | 登记进「白问核查」 |
