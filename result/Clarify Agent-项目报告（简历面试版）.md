## 〇、一句话定位与主要贡献

**Clarify Agent——通过自主追问挖掘用户需求的 RAG 决策规划系统。** 独立设计并落地了一套可量化、可复现的评估与产品化体系，用对照实验证明"追问式需求澄清"与"RAG 事实锚定"的独立价值，并把验证有效的方案反哺产品。

**主要贡献**：基于真实需求发现与产品竞对分析，搭建产品、持续迭代，并独立执行 A/B 测试——完成"发现问题 → 定义方案 → 验证价值 → 反哺产品"的完整闭环。

> 这不是一个只针对单一用户场景的系统：**能力层与知识层解耦，替换知识库即可迁移到考研规划、职业发展等场景**；旅游是首个验证场景。

---

## 一、项目背景与目标

- **场景起点**：用户查旅游攻略时，公共平台有大量经验信息，但整理起来耗时费力；大家用同样的经验贴，方案千篇一律、缺乏针对性；用户对自己的需求往往认识不足。
- **AI 的机会与缺口**：AI 有知识库、生成速度快，但用户很难问一个好问题、很难阐述清楚自己的需求，导致 AI 难以给出令人满意的针对性答案。
- **我的角色**：负责**产品设计 + 评估体系搭建**（非单纯测试执行）。
- **核心目标**：把"这个 Agent 到底好不好、好在哪"从体感判断转化为**可量化、可复现、可对外展示**的结论，并据此决定产品迭代方向。
- **要证明的两件事**（全项目主线假设）：
  - H1：**先追问**是否比直接生成更能命中用户真实需求；
  - H2：**二次检索 + RAG** 是否比单轮生成更能提升事实准确性。

---

## 二、需求发现与用户痛点

由场景观察抽象出三类可观测痛点，并对应到后面的三层指标：

| 痛点         | 表现                                | 对应指标层 |
| ---------- | --------------------------------- | ----- |
| **① 需求痛点** | 用户难以挖掘自己的全部需求，因而拿不到针对性规划；问不对，答案就偏 | 需求侧   |
| **② 事实痛点** | 攻略里的门票、开放时间、价格等硬信息是否可靠，用户无法自行核验   | 事实侧   |
| **③ 体验痛点** | 用户希望快速拿到结果、少花时间，不愿在信息海洋里反复整理      | 体验侧   |

**关键判断**：不能只看"方案写得全不全"，必须把**需求理解**与**事实可信**拆成两类独立指标——这是后面指标体系与三模式实验的起点，也是系统可迁移的评估基础。

**痛点不止于旅游**：考研规划的目标院校、基础与备考周期，职业规划的方向、经验与转型约束，同样存在"说不清需求 + 事实要靠谱 + 要快"这三类问题——所以这套方法从一开始就是按可迁移的方式设计的。

## 三、竞品分析与差异化定位

> 以下为基于公开产品形态的**定性判断，未经实测竞品对比**。

| 形态                        | 强项                                         | 短板                    |
| ------------------------- | ------------------------------------------ | --------------------- |
| 公共平台（攻略社区 / 招生信息站 / 招聘平台） | 信息多、可检索                                    | 整理耗时间、缺针对性、千人一面       |
| AI 助手（聊天式 AI）             | 便捷迅速、生成快                                   | 缺少针对用户隐藏需求的解决方案，事实无锚定 |
| **Clarify Agent（本系统）**    | **自主追问 + 会话记忆 + RAG 事实锚定 + 工具调用；换知识库即可迁移** | 迁移效果依赖新知识库的质量         |

**差异化结论**：不做"生成得更多"，而做"**先问对问题 + 说得有据**"。用自主追问解决需求对齐，用知识库解决事实可信——把这两件事做成可复用的系统能力，而不是某一个场景的定制功能。

## 四、产品描述

### 4.1 项目搭建

手写 Agent 循环（不依赖 LangChain 等框架）；MCP 接入联网与文件系统；RAG 知识向量库（`bge-m3`）做检索；Web 页面与 CLI 双入口；流式输出与多轮对话记忆。**知识库以目录为单位注入，能力层与领域知识解耦。**

### 4.2 核心功能与用户流程

`用户提出需求 → 多轮 Agent 细节询问 → 隐藏需求澄清 → 结合 RAG 检索提供可靠事实材料 → 生成方案`。追问由模型自主决定，不使用固定问卷；B2 模式在终版前额外做一次二次检索并重生成。

### 4.3 三步迭代路径（V1 即 MVP）

| 版本          | 做了什么                                                    | 解决的问题                                    |
| ----------- | ------------------------------------------------------- | ---------------------------------------- |
| **V1（MVP）** | 简单接入 MCP 与 RAG 的 Agent 问答                               | **最小可行产品**：用最小成本打通"能查、能生成"的基础链路，验证主链路可行性 |
| **V2**      | 接入 `ask` 询问工具：每轮用户提出问题后，Agent 不直接给答案，必要时追问用户尚未提供的隐藏潜在需求 | 从"答得快"变成"问得准"，解决需求对齐                     |
| **V3**      | 优化 RAG 流程：沿用上一版本的问答环节，用追问信息重新检索知识、重生成终版                 | 节省检索成本与时间，同时提高答案的需求满足率与事实可靠性             |

V1 就是产品的 **MVP（最小可行产品）**：先用一个能跑通的最小闭环验证"检索 + 生成"链路可行，再决定往哪个方向迭代——避免一开始就重投入。V3 既是产品迭代的结果，也是后面 A/B 测试里的 B2 模式——**迭代与实验用的是同一套方案**，这也是结论能直接反哺产品的原因。

### 4.4 三层可迁移架构（核心产品判断）

| 层级  | 内容                         | 换场景时      |
| --- | -------------------------- | --------- |
| 能力层 | 追问引擎、多轮记忆、工具调用、终版重生成       | 无需改动      |
| 知识层 | RAG 检索与事实锚定机制              | 替换领域知识库文档 |
| 评估层 | A/B/B2 实验设计、三层指标体系、5 类题库结构 | 替换题目与隐藏信息 |

这一分层是"一套系统、多个场景"的前提：旅游只是首个验证场景，考研规划、职业发展规划可复用同一套能力与评估方法。

### 4.5 三模式设计与关键取舍（体现产品判断）

| 模式     | 定义                                           | 用途    |
| ------ | -------------------------------------------- | ----- |
| **A**  | 不追问，直接生成                                     | 对照基线  |
| **B**  | 先追问、拿到答复再生成                                  | 验证 H1 |
| **B2** | 复用 B 的**完整交互轨迹**，移除草稿，补入二次检索资料，**禁用工具**重生成终版 | 验证 H2 |

三个关键取舍：

- **B2 复用 B 的轨迹**——保证行为（act）一致，把 RAG 作为唯一变量隔离出来，否则无法干净归因；
- **终版阶段禁用工具**——避免二次检索后工具调用污染对照；
- **固定随机种子 EVAL_SEED**——保证模拟用户与主模型可复现，结果可信、可复跑。

## 五、A/B 测试：假设、指标、过程与结果

### 5.1 假设

- H1：自主追问能显著提升需求满足率与要点覆盖率；
- H2：二次检索 + RAG 能显著提升硬信息准确率、降低瞎编率。

### 5.2 指标设计（三层结构）

| 层级         | 指标                 | 回答什么问题           |
| ---------- | ------------------ | ---------------- |
| 需求侧 · 需求理解 | 需求满足率、要点覆盖率        | "有没有听懂、有没有覆盖到"   |
| 事实侧 · 事实可靠 | 瞎编率、硬信息准确率         | "说得准不准、有没有胡编"    |
| 体验侧 · 白问论述 | 白问次数（辅以行程冲突数、追问轮数） | "追问是否打扰、方案是否可执行" |

设计原则：**不让单一指标既当运动员又当裁判**——需求侧与事实侧用不同数据源，同向变化才有说服力。这套指标结构不依赖具体场景，可随系统迁移复用。

### 5.3 测试集构建

CSV 文件构建 **20 个 case**，按需求描述清晰程度分 **5 类**：

1. 完全类（说得很全）
2. 说一半
3. 模糊类
4. 不合理
5. 不该答应

每个 case 都提前结构化存档两类基准信息：**用户隐藏需求**（未告知 Agent、需要它主动追问才透露）与**好攻略应覆盖的要点**。这套结构既是需求命中率的判据，也可复用到新场景。

### 5.4 测试流程

| 步骤       | 做法                                                              | 关键机制                                                                                   |
| -------- | --------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| **① 跑题** | 调 API 借 LLM 模拟用户与 Agent 互动，回答 Agent 的追问                         | **巧思**：case 里已有的隐藏信息如实作答，未设定的信息合理即兴；若 Agent 问询超过 15 轮，模拟用户主动要求给出最终方案——**节省成本、防止无限轮对话** |
| **② 裁判** | 调 API 借 LLM 作 AI 裁判，输入用户问题、Agent 与用户对话、检索知识、最终攻略，输出各指标打分明细与依据表格 | 六块结构化输出，分数与依据一一对应                                                                      |
| **③ 录入** | 将裁判输出的 txt 数据录入预先准备的 Excel，比对不同 case 表现与不同版本产品的指标差异             | 8 张表分区，自动核对与兜底                                                                         |

### 5.5 三个可靠性巧思

1. **版本 3 沿用版本 2 的问答环节**：把 V2 得到的问答信息拿去检索知识、重新输出新版答案。既免去每轮询问都检索的成本与时间，又控制了 ask 环节一致——**两个版本的核心差异只在信息检索**，测评数据差异来源可控、归因有说服力。
2. **裁判幻觉前置抑制**：裁判模型存在幻觉、会漏点缺点，因此针对每个 case 提前写好待评价的需求点与要点，让裁判在既定骨架内判断，降低幻觉。
3. **录入环节兜底**：裁判模型的评价明细写好后，仍可能出现分数与明细依据不对应；录入时用代码抓取裁判输出 txt，比对分数与明细依据，发现逻辑矛盾**以明细为准**——降低幻觉率与数据错误率。

> 一句话概括方法论：**代码负责计数、兜底与骨架预填，LLM 只做语义判断**，规避大模型数数不可靠的问题。

### 5.6 结果（数据来源：项目成绩单，2026-11-19）

| 指标     | A     | B     | B2        | 解读                      |
| ------ | ----- | ----- | --------- | ----------------------- |
| 需求满足率  | 36.4% | 76.1% | 77.5%     | 追问 **+40pp**；B2 持平符合预期  |
| 要点覆盖率  | 37.5% | 66.3% | 74.0%     | 追问 +28.8pp，RAG 再 +7.8pp |
| 平均行程冲突 | 0.9   | 0.4   | 0.4       | 追问使冲突减半                 |
| 硬信息准确率 | —     | 50.5% | **77.0%** | RAG **+26.6pp**，最硬的证据   |
| 瞎编率    | —     | 27.2% | 17.8%     | −9.4pp，仅作辅证             |

### 5.7 业务 / 产品意义

- **H1 成立**：追问把需求满足率从三成多拉到七成六——"先问对问题"是最大杠杆；
- **H2 成立**：硬信息准确率从五成到七成七——RAG 的价值在"说得准"，不在"问得懂"；
- **B2 需求满足率几乎不涨是正确的**：它复用 B 的澄清结果，只补知识料。该平的就平、该涨的涨，说明实验设计自洽，结论可外推到真实产品，也可随系统迁移到其他规划场景。

## 六、项目的两个核心优势价值

### 优势一：问对问题是最大的杠杆

**AI 固然好用，但一个好的提示词、一个好问题，可以显著提高解决问题的效率；而大部分用户无法提出一个特别精准的问题——问不对，那就把"问什么"交给 Agent，由它主动提问、引导用户给出细节。**

> **用户负责说什么，Agent 负责问什么。** 与其把用户训练成提示词专家，不如让 Agent 主动把问题问出来——把提问的认知负担从用户侧转移到系统侧。

这是 Clarify Agent 的设计原点，也是数据里最大的单一杠杆：一次自主追问，需求满足率从 36% 提到 76%（**+40pp**）。它不是"答得更多"，而是"先问对问题"，把复杂留给自己、把简单留给用户。

### 优势二：迁移优势

旅游只是测试的首用场景。系统能力层与知识层解耦，**只需替换知识向量库，同一套追问引擎与评估体系即可迁移到其他规划场景**——考研规划、未来工作发展规划等都适用。一次投入，多场景复用，边际成本随场景增加而递减。把能力做成系统，把场景做成可插拔的知识库，放大复用价值。

## 七、关键决策依据（面试加分项）

1. **架构解耦，为迁移做准备**：把知识库做成可替换目录、能力层不绑定领域，是"一套系统多个场景"的工程前提——这决定了项目价值不局限于旅游。
2. **统一计分口径**：边界题中"诚实拒绝不合理请求"本质是正向需求，应计入需求满足率，据此取消特殊规则、全题统一计分——保证尺子一致，也让评估方法可跨场景复用。
3. **反哺产品**：验证有效后，把 B2 接入真实产品（CLI 与 Web 默认启用），评测仍保留三模式对照，实现"实验结论 → 产品迭代"的闭环。

---

## 八、遇到的限制与改进方向

- **样本量有限**（20 题）：单题权重 5%，小数位差异不宜过度解读；
- **裁判一致性风险**：同类表述的评分一致性仍需提升，建议上线前人工抽检；
- **迁移的待验证项**：架构支持换库即用，但新场景的效果需配套领域知识库与题目集验证——这是下一步重点；
- **方向**：扩大样本、引入人工语义复核、把指标体系固化为自动化看板。

## 九、项目复盘与个人贡献

**个人贡献**：① 基于需求发现与竞对分析定义产品方向；② 搭建产品并完成 V1→V3 三轮迭代；③ 设计三模式对照与三层指标体系；④ 构建并迭代 20 题评估集、统一计分口径；⑤ 独立执行跑题—裁判—录入全流程 A/B 测试；⑥ 推动 B2 方案落地产品，形成闭环；⑦ 将项目抽象为可迁移的规划系统。

**方法论沉淀**：

- **先做 MVP 再迭代**——V1 只求最小闭环跑通，验证主链路后再逐版叠加能力，避免过早重投入；
- 验证一个机制的价值，必须先**隔离变量**（B2 复用 B 轨迹）；
- 评估口径必须统一，保证不同模式、不同题目在同一把尺子上比较；
- **实验要可复现**，固定随机种子、结构化存档，让结论经得起复核；
- 做产品要区分"能力"与"场景"——**把能力做成系统、把场景做成可插拔的知识库**，才能放大复用价值；
- **问对问题是最大的杠杆**——把提问的负担从用户侧转移到系统侧，是规划类 Agent 的核心产品判断。

## 十一、面试讲述重点

**30 秒电梯陈述**：

> "我实习时做了 Clarify Agent——一个通过自主追问挖掘用户需求、并用 RAG 锚定事实的决策规划系统。核心判断是：大部分用户说不清自己的需求，与其教用户写更好的提示词，不如把'问什么'交给 Agent。它不是只针对旅游的：把知识库换掉，同一套追问和评估体系就能迁移到考研规划、职业规划。旅游是第一个验证场景。为了验证价值，我设计了 A/B/B2 对照实验：A 直接生成、B 先追问、B2 在 B 基础上做二次检索。结论是追问把需求满足率从 36% 提到 76%，RAG 把硬信息准确率从 50% 提到 77%。更有意思的是，B2 的需求满足率基本没涨——但它复用的是 B 的追问结果，只补知识料，说明变量隔离做对了。最后我把这套方案落地到了产品。"

**建议主动带出的三个记忆点**：

① **问对问题是最大的杠杆**——用户负责说什么，Agent 负责问什么，把提问负担转移到系统侧；② **该平的就平、该涨的涨**，证明实验自洽、归因干净；③ 从评估到产品落地的闭环意识。

**可能被追问 & 应答方向**：

- *"为什么让 Agent 追问，不直接生成？"* → 用户说不清需求是规划类场景的普遍痛点；+40pp 的需求满足率提升证明"先问对问题"是最大杠杆。
- *"换个场景真的能用吗？"* → 架构上检索器以目录注入、能力层不绑定领域，换知识库和题库即可；下一步需在新场景做一轮效果验证。
- *"为什么 B2 需求满足率没涨？"* → 它复用 B 的澄清结果，只补知识料，证明变量隔离成功，不是失败。
- *"样本才 20 题够吗？"* → 承认局限，强调结论来自多指标同向印证而非单点，并给出扩样方案。
- *"裁判准吗？"* → 坦诚评分一致性风险，说明已用前置要点骨架 + 代码计数 + 录入兜底降低误差，并提出人工复核改进。
