# A/B/B2 测试说明：三个流程、三种模式、材料口径与产出

> 口径版本：2026-11-19（统一计分：所有题目一律既算需求满足率、也算打分表命中率，不再有“拒答题只算打分命中”的特殊口径；4 道边界题的隐藏信息改写为正向需求清单。B2 沿用原会话、排除本轮草稿、单次禁用工具生成终版）。本文与当前 `eval/run_ab.py`、`eval/judge.py`、评估工作区 `自动录入.py` 和成绩单公式保持一致。

> 本文只说明**评估流程**。产品终端/网页入口当前没有启用 B2 的二次检索；`src/agent.py`、`src/chat_openai.py` 里保留的是 B2 支撑能力，A/B 原路径不受影响。

## 0. 这套测试到底在比什么

整套测试是三个流程接力：

```text
评估任务集 CSV
   │
   │ ① 跑题：读题、模拟用户追问、生成攻略
   ▼
对话记录/
   │
   │ ② 裁判：按固定 6 块输出打分明细
   ▼
裁判输出/
   │
   │ ③ 写入：把明细搬进 Excel，公式自动汇总
   ▼
攻略Agent评估成绩单.xlsx
```

三种模式：

| 模式 | 做法 | 用来回答的问题 |
|---|---|---|
| **A** | 不给 Agent 注册 `ask_user`，直接根据首轮检索结果生成攻略 | 不追问会怎样？ |
| **B** | 注册 `ask_user`，由“模拟用户 AI”按 CSV 隐藏设定回答追问，然后生成攻略 | 先澄清再生成有没有用？ |
| **B2** | **复用 B 的完整 messages 和追问轨迹**，不再重新追问；用“首问 + B 的追问问答”做二次检索，排除最后完整草稿、追加资料，单次禁用工具生成终版 | 在交互轨迹固定的前提下，二次检索与终版处理组合有没有增益？ |

一句话概括 B2 的设计目的：

> **控制住 B 与 B2 的用户交互 act 一致，比较二次检索与终版生成这一组处理的效果。**

更精确地说，B 和 B2 固定的是：

- 用户首问；
- Agent 追问的问题；
- 模拟用户的回答；
- 追问轮数；
- 白问核查面对的问答轨迹。
- B 产出的完整会话历史；B2 恢复该历史后只排除最后一条完整攻略草稿。

B 和 B2 主动放开的是：

- 终版生成前是否做二次检索；
- 终版参考资料是否变成“首轮 + 二轮合并去重”；
- 是否排除 B 的完整草稿，并追加资料及最终输出指令，再做一次禁止工具的终版生成。

所以：

- **A vs B**：看“追问澄清”带来的变化；
- **B vs B2**：看“澄清信息回流 RAG + 排除草稿 + 禁止工具生成终版”带来的变化，不能把结果单独归因于二次检索；
- 不能把 B2 的差异简单说成“用户配合不同”或“追问策略不同”，因为这些被复用了。

## 1. 公共输入

### 1.1 评估任务集 CSV

默认路径：

```text
<项目根目录>/result/评估任务集模板.csv
```

关键列：

| 列 | 内容 | 谁读 | 用途 |
|---|---|---|---|
| B 列 | 用户原话 | 跑题脚本 | 当作用户首问 |
| C 列 | 题目类型 | 人工 | 模糊 / 说了一半 / 说得很全 / 知识库里没有 / 不合理要求 / 不该答应 |
| D 列 | 藏起来的信息 | 跑题脚本、裁判 | 模拟用户的回答设定；同时也是裁判判需求满足的完整需求清单（所有题通用） |
| E 列 | 打分表 | 裁判 | 判断好攻略必须覆盖的点；统一为每题 5 条 |
| F 列 | 备注 | 人工 | 这道题想测什么，不算分 |

注意：裁判判“需求满足”时，分母始终是 CSV 的**完整需求清单**，不是只看 Agent 有没有问出来。没问出来的隐性需求，没满足就是没满足。

【2026-11-19 统一计分】所有题目一律既算需求满足率、也算打分表命中率：

- **题目类型统一矫正**：按用户首问实际给的信息量归类。T02、T05 从“模糊”改为“说了一半”（都给出了部分明确信息）。
- **打分表统一 5 条**：20 题的分母全部为 5，要点覆盖率可横向比较。T01 打分表第 1 条从锁死目的地的“行程含西湖及周边水乡”改为“含自然风光类景点”。
- **隐藏信息不再留空**：T10（月球）、T11（1天15景）、T12（逃票）、T19（东京）原先填“无”，现改写为**正向需求清单**（如 T10“真实需求是听到助手如实说明月球游无法规划”），每题 2 条。这类边界题的需求满足率照常计算——满足率越高，说明 Agent 越能识别并正确回应边界请求。
- **不再有特殊口径**：CSV 已删除“计分口径”列；裁判和录入对所有题一视同仁，需求满足率全部进 A-B 对比平均。

## 2. 流程①：跑题

脚本：`eval/run_ab.py`  
运行位置：项目根目录  
是否花钱：会调模型 API，花钱

### 2.1 常用命令

```bash
uv run --cache-dir .uv-cache python eval/run_ab.py
# 全部题目，默认 A,B

uv run --cache-dir .uv-cache python eval/run_ab.py --tasks T01
# 只跑 T01 的 A,B

uv run --cache-dir .uv-cache python eval/run_ab.py --tasks T01 --modes B2
# 只跑 T01 的 B2；脚本会自动补跑 B，因为 B2 要复用 B 的追问轨迹

uv run --cache-dir .uv-cache python eval/run_ab.py --modes A,B,B2
# 三模式全跑，推荐正式评估用这条
```

【修改】指定 B2 时，脚本会确保本轮 B 先成功运行；缺少 B 则自动插入，即使显式写 `--modes B2,B` 也调整为先 B 后 B2。这是为了保证：

1. B2 有本轮 `Txx-B.md` 和 `Txx-B-messages.json` 可以复用；
2. B2 的追问记录和 B 完全一致；
3. 不会把模拟用户的随机性带进 B2。

本轮 B 失败时，该题 B2 不继续读取旧产出。旧评测若只有 MD、没有完整 messages 文件，需要重新跑 B，不能仅凭问答摘要还原并冒充原会话。

### 2.2 模式 A

构造 Agent 时**不传** `ask_user_callback`：

- `ask_user` 工具根本不注册；
- Agent 无法向模拟用户追问；
- 直接用首轮检索资料生成攻略；
- 追问轮数恒为 0。

### 2.3 模式 B

构造 Agent 时传入“模拟用户 AI”回调。

模拟用户的回答规则：

- CSV D 列里设定过的信息：如实回答；
- 设定外的问题：合理即兴回答，但不能和设定矛盾，也不能新增硬性需求；
- “还有什么要补充”这类开放式收口问题：把设定里还没说过的都倒出来；
- 最多认真回答 15 个问题，第 16 问起统一回答：`信息足够了，请直接出攻略`；
- 模拟用户模型调用失败时，退回关键词匹配，不中断跑题。

模式 B 的输出包含完整追问记录和 B 的最终攻略；【修改】成功后另存 `Txx-B-messages.json`，其中 `messages` 字段记录最终攻略生成后完整的 `llm.messages`，并保存首轮资料、题目、问答、草稿、`format_version` 与 `run_id`，供 B2 恢复和核对同批结果。

### 2.4 模式 B2（复用 B 完整历史继续生成）

模式 B2 **不再自己跑一遍 Agent 主循环，也不再问模拟用户**。

实际步骤：

1. 读取本轮成功的 `Txx-B.md` 与 `Txx-B-messages.json`，核对题目和来源；
2. 从里面解析出：
   - B 的追问问答记录；
   - B 的最终攻略，作为 B2 草稿留档/异常回退；
3. 恢复 B 的完整 messages，并使用其保存的实际首轮检索资料；裁判对应读取 `Txx-B-context.txt`，缺少时才兼容共享的 `Txx-context.txt`；
4. 用「用户首问 + B 的全部追问问答」合成 query，做一次二次检索；
5. 二次资料写入 `Txx-B2-context2.txt`；
6. 把首轮资料与二次资料合并，仅全文完全相同的笔记去重；正文内部的重复文字、换行和空白原样保留；
7. 【修改】沿用原 messages 生成终版：
   - 只移除本轮最后一条完整攻略草稿，保留原系统指令、用户消息、ask 调用和答复及其他工具结果；
   - 追加一条合并后的参考资料及最终输出指令，不重新整理成一组干净 messages；
   - 本次请求在代码层关闭工具，不执行 `ask_user` 或 MCP 工具；后续普通请求仍可使用工具；
   - 终版按普通 assistant 消息写入历史，不再专门回填终版记忆；
8. 输出 `Txx-B2.md`；
9. 把 B 的攻略另存为 `Txx-B2-draft.md`，仅供调试对照，裁判不读。

注意两点：

- B2 从最终请求中排除 B 的完整攻略，依据原会话需求和补充资料重新生成；不是把 B 攻略原样粘过去。
- 产品与 eval 使用同一终版生成策略：沿用历史、排除最后草稿、追加资料、单次禁止工具。eval 的历史来自 B 的保存文件；产品直接使用当前 Agent 的 messages。新版结果标记流程版本 `continue-history-v1`，B/B2 共享同一个运行标识 `run_id`。旧“干净 messages”结果不符合新版流程，需重跑 B/B2 和裁判，不能直接沿用或混判。

### 2.5 跑题产出

写到评估工作区 `对话记录/`：

| 文件 | 内容 |
|---|---|
| `Txx-A.md` | A 模式记录：题号、模式、追问轮数 0、题目、最终攻略、流程版本和运行标识 |
| `Txx-B.md` | B 模式记录：题号、模式、追问轮数、题目、完整追问记录、最终攻略、流程版本和运行标识 |
| `Txx-B-messages.json` | 【修改】B 的完整会话、首轮资料和配对信息，供 B2 恢复；缺少时需重跑 B |
| `Txx-B2.md` | B2 模式记录：追问记录和运行标识与 B 相同，流程版本为 `continue-history-v1`，攻略为新终版 |
| `Txx-A-context.txt` / `Txx-B-context.txt` | 【修改】A/B 各自实际使用的首轮资料；裁判优先读对应模式文件 |
| `Txx-context.txt` | 共享首轮资料的旧格式兼容文件，可能被后运行的模式覆盖，不作为新版裁判的优先来源 |
| `Txx-B2-context2.txt` | B2 二次检索资料 |
| `Txx-B2-draft.md` | B2 被替换掉的草稿，也就是 B 的攻略，仅调试用 |
| `Txx-模式.error.txt` | 某题某模式失败时才生成，其他题继续执行 |

全部成功时，20题 × 3模式会产出60份攻略记录，另有对应模式首轮资料、共享兼容资料、20份 B 完整历史、20份 B2 二次资料和20份草稿留档；这些是产出文件数量，不是模型调用次数。

## 3. 流程②：裁判

脚本：`eval/judge.py`  
运行位置：项目根目录  
是否花钱：会调模型 API，花钱

### 3.1 常用命令

```bash
uv run --cache-dir .uv-cache python eval/judge.py
# 裁判所有已跑完的题

uv run --cache-dir .uv-cache python eval/judge.py --tasks T01
# 只裁判 T01

uv run --cache-dir .uv-cache python eval/judge.py --dry
# 只拼提示词，不调模型，不花钱
```

### 3.2 裁判读什么

裁判输入由五类材料拼成：

| 材料 | 来源 | 用途 |
|---|---|---|
| 攻略 | `Txx-A.md` / `Txx-B.md` / `Txx-B2.md` | 被检查对象；B2 读终版 |
| 追问记录与轮数 | 同上 | 用来核查白问；B2 用的是复用自 B 的同一份记录 |
| 需求清单 | CSV D 列 | 判需求满足，A/B/B2 同一分母 |
| 打分表 | CSV E 列 | 判要点覆盖 |
| 知识库资料 | 见下表 | 判攻略里的说法有没有依据 |

知识库资料的口径：

| 模式 | 裁判使用的资料 |
|---|---|
| A | 优先 `Txx-A-context.txt`，缺失时兼容 `Txx-context.txt` |
| B | 优先 `Txx-B-context.txt`，缺失时兼容 `Txx-context.txt` |
| **B2** | B 的首轮资料（优先 `Txx-B-context.txt`）+ `Txx-B2-context2.txt` **合并去重后**的资料 |

这里要特别注意：

> B2 裁判不是只看二次检索资料。  
> B2 终版是用首轮 + 二轮合并资料生成的，所以裁判也必须看合并资料，否则首轮资料支持的事实会被误判成“无依据”。

【修改】裁判在调用模型前检查结果有效性：有 `.error.txt` 失败标记的结果会被跳过；B2 还必须属于 `continue-history-v1`，且与本轮 B 的题目、运行标识配对。旧版、不配对或本轮失败的 B2 不进入裁判，需先重跑 B/B2，再运行裁判。

【修改】正式裁判跳过上述无效结果时，若 `裁判输出/` 已有对应的旧评分，会把它可逆移动到 `裁判输出/历史结果/<stem>-<uuid>.txt.archived`（例如 `T01-B2-<uuid>.txt.archived`），不删除内容；末缀 `.archived` 避免外部 `*.txt` 扫描将旧分数再次录入。`--dry` 只显示跳过原因，不移动评分，也不创建归档目录。

### 3.3 裁判输出

写到评估工作区 `裁判输出/`：

```text
Txx-A.txt
Txx-B.txt
Txx-B2.txt
```

每份输出固定 6 块：

| 块 | 内容 | 主要去向 |
|---|---|---|
| 一、得分 | 需求满足 x/y、打分表命中 x/y、行程冲突 N 处、事实性陈述 N 条、白问次数 N 次 | 成绩单数字列 |
| 二、需求与打分表明细 | 每条检查项的判定和依据 | 人工抽查裁判 |
| 三、事实句核查 | 攻略原句、有无依据、出处 | 瞎编核查表 |
| 四、硬信息核查 | 信息项、攻略值、资料值、对/错 | 硬信息核查表 |
| 五、行程冲突 | 冲突类型、涉及安排、原因 | 总数进成绩单，明细人工复核 |
| 六、白问核查 | 每轮追问一行：问题、答复、是否白问、依据 | B 写入白问核查表；B2 不重复写 |

每份攻略是独立一次裁判调用，互不污染。

运行位置：`<项目根目录>/result`  
是否花钱：不花钱

```bash
cd "C:/Users/tangjiapeng/Desktop/program/Clarify Agent/result"
python 自动录入.py
```

### 4.1 Excel 结构

成绩单一共 8 张表：

1. `A-B对比`
2. `成绩单`
3. `瞎编核查`
4. `硬信息核查`
5. `白问核查`
6. `填写说明`
7. `瞎编核查B2`
8. `硬信息核查B2`

### 4.2 自动录入写什么

| 写入位置 | 写入内容 |
|---|---|
| `成绩单` 对应行 | 追问轮数、需求满足 x/y、打分表命中 x/y、行程冲突数 |
| `瞎编核查` | B 的事实句核查明细 |
| `瞎编核查B2` | B2 的事实句核查明细 |
| `硬信息核查` | B 的硬信息核查明细 |
| `硬信息核查B2` | B2 的硬信息核查明细 |
| `白问核查` | 只登记 B 的白问明细；A 固定 0，B2 不重复登记 |

B2 为什么不写白问核查表：

- B2 复用 B 的追问问答，交互轨迹完全相同；
- 如果 B2 再写一遍白问明细，会把同一批追问重复计数；
- 成绩单里 B2 行的白问次数公式，直接数同一题 B 模式登记在 `白问核查` 表里的“是”。

当前公式口径：

```excel
A 行：白问次数 = 0
B 行：COUNTIFS(白问核查!题号列, 本题, 白问核查!模式列, "B", 白问核查!终判列, "是")
B2 行：COUNTIFS(白问核查!题号列, 本题, 白问核查!模式列, "B", 白问核查!终判列, "是")
```

所以 B2 的白问次数天然等于 B，这正是“交互 act 固定”的体现。

### 4.3 内置防呆

自动录入会做这些保护：

- 同题重复录入前，先清掉该题旧记录，不会重复堆叠；
- 文件名按 `Txx-B2.txt` 优先匹配，避免把 B2 误认成 B；
- A 模式只填数字列，不进核查表；
- B2 的瞎编/硬信息写专用表，不和 B 混；
- B2 不重复写白问核查表；
- 裁判块一的白问次数和表六“是”的行数不一致时会提示人工核对；
- 数字没解析到时会提示手补。

## 5. 公式怎么读结论

核查表里的终判 → 自动汇总计数 → 自动算指标 → `A-B对比` 表汇总。

核心读法：

| 对比 | 含义 |
|---|---|
| **B - A** | 追问澄清带来的变化 |

| 指标 | 方向 |
|---|---|
| 需求满足率 | 越高越好 |

| 硬信息正确率 | 越高越好 |

B2 的重点不是“又问了一遍”，而是：

## 6. 人工还要做什么

自动化只做到“裁判初判”和“录入”，最终判定仍需人把关。

### 6.1 核查表终判

重点核这些行：

- 瞎编核查里标“无”的行；
- 硬信息核查里标“错”的行；
- 白问核查里标“是”的行。

AI 初判只是初判，最终以你人工确认的终判为准。

### 6.2 抽查裁判

看裁判输出的第二大块“需求与打分表明细”，确认它有没有误判：

- 明明满足却判不满足；
- 明明没满足却判满足；
- 把隐性需求重复计数；
- 依据引用错模式或错资料。

发现裁判判错时，可以直接改成绩单数字，并在备注里记一句。

## 8. 注意事项

- **费用**：【修改】B 每轮追问会多一次模拟用户调用；B2 在原历史上增加一次终版生成和一次二次检索。本次生成不携带工具定义，但保留原会话和补充资料，费用取决于输入输出长度。单独跑 `--modes B2` 时，脚本会自动补跑 B，所以费用包含 B + B2。
- **冒烟顺序**：正式全量前，先跑 `--tasks T01 --modes A,B,B2`，确认跑题、裁判、录入三流程都通。
- **MCP 子进程**：A/B 跑题会创建 MCP 子进程；B2 恢复已有历史后只生成终版，不需要再启动 MCP。
- **Excel 锁**：成绩单被 Excel/WPS 打开时，自动录入可能写不进去；录入前先关闭该文件。
- **别乱跑 builder**：`.攻略Agent评估成绩单.ref/build.py` 是造空成绩单的施工脚本，每次运行会整份覆盖重建，已录入数据会被清空。只有改结构或推倒重来时才用，且先备份。
- **材料边界**：不要把“裁判提示词、CSV 隐藏需求、模拟用户设定”直接塞给旅游攻略 Agent。它们只属于评估侧。Agent 只能看到用户原话和检索资料。
