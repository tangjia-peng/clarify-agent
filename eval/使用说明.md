# eval/ 使用说明（A/B/B2 测试全自动化）

三个脚本接力，跑完 20 题只要三条命令。全部在**项目根目录**执行。

三种模式：

- **A**：不追问，直接生成（基线）
- **B**：先追问再生成（测"追问澄清"有没有用）
- **B2**：【修改】复用 B 的完整 messages 和追问问答，用「首问+追问回答」重新检索知识库；排除 B 最后一条完整攻略草稿，追加合并后的参考资料，单次禁用工具生成终版。B2 不新增追问，白问与 B 相同。

B/B2 固定追问轨迹，比较“二次检索＋排除草稿＋禁止工具生成终版”这一组处理；不能仅凭该对比认定二次检索或某一步单独带来了提升。终端与网页当前仍默认不启用 B2。

## 1. 跑题（会调用你的模型 API，产生费用）

```
uv run --cache-dir .uv-cache python eval/run_ab.py
# 默认只跑 A,B；三模式全跑请加 --modes A,B,B2
```

- 只跑某几题：`--tasks T01,T02`；只跑某模式：`--modes B2`
- 模式 A：不给 Agent 提问工具，直接生成攻略
- 模式 B2 冒烟：`--tasks T01 --modes B2`（建议先单题试跑）
- 模式 B：Agent 追问时，由一个**大模型扮演的"模拟用户"**回答——CSV「藏起来的信息」是它的设定：
  设定内如实答；设定外（如"坐高铁还是飞机"）合理即兴答，但不得与设定矛盾、不得新增硬性需求；
  只有"还有什么要补充"这类开放式收口问题才会倒出剩余设定。模型调用失败自动退回关键词匹配，不中断
- 追问上限：模拟用户**最多认真回答 15 个问题**，第 16 个起一律答"信息足够了，请直接出攻略"
  （防止 Agent 无限追问拖垮跑题；对话记录里这些收口回答都会留痕，追问轮数如实计数）
- 产出：`<评估工作区>/对话记录/T01-A.md`、`T01-B.md`、`T01-B2.md`（含追问轮数、记录、流程版本和运行标识）；各模式实际首轮资料分别保存在 `T01-A-context.txt`、`T01-B-context.txt`，共享 `T01-context.txt` 仅作旧格式兼容
- 【修改】B 成功后另存 `T01-B-messages.json`，其中包含完整会话 `messages`、首轮资料、题目、问答、草稿及配对信息，供 B2 恢复；只有旧 MD、缺少此历史文件时，必须重跑 B，不能用问答摘要代替原会话。
- 【修改】新版流程版本为 `continue-history-v1`，B/B2 的运行标识 `run_id` 必须一致。旧“干净 messages”流程的结果需重跑 B/B2 及裁判，不会自动转成新结果。
- B2 额外产出：`T01-B2-context2.txt`（二次检索资料，裁判核终版用）、`T01-B2-draft.md`（被替换的草稿，仅调试，裁判不读）
- 失败的题会写 `T01-B.error.txt`，不影响其他题继续跑
- 【修改】B2 必须使用本轮成功的 B；显式指定 `--modes B2,B` 时也先运行 B。本轮 B 失败则跳过该题 B2，不借用上次结果。
- 注意费用：模式 B 每轮追问会多一次"模拟用户"的模型调用（输入很小，费用低）

## 2. 裁判（调用模型 API）

```
uv run --cache-dir .uv-cache python eval/judge.py
```

- 读上面的产出 + CSV 的打分表和「藏起来的信息」（作为用户完整需求清单，A/B/B2 同口径判需求满足），按固定 6 块格式打分（含【六、白问核查】明细表）
- 【修改】裁判优先使用各模式自己的首轮资料：A 读 `T01-A-context.txt`，B 读 `T01-B-context.txt`；B2 把 B 首轮资料与 `T01-B2-context2.txt` 合并后核终版事实。仅全文完全相同的笔记去重，正文内部的重复事实保留；缺少模式首轮文件时才兼容读取 `T01-context.txt`。
- 【修改】有 `.error.txt` 失败标记的结果、缺少新版流程标记的 B2、与 B 运行标识或题目不配对的 B2，会被裁判跳过；应先重跑对应 B/B2，再重新运行裁判。
- 【修改】正式裁判跳过无效结果时，会把已有同名旧评分移动到 `裁判输出/历史结果/<stem>-<uuid>.txt.archived`（例如 `T01-B2-<uuid>.txt.archived`），内容完整保留，可移回恢复；归档末缀避免外部 `*.txt` 扫描继续录入旧分数。`--dry` 只报告，不移动文件或创建归档目录。
- 产出：`<评估工作区>/裁判输出/T01-A.txt`、`T01-B.txt`、`T01-B2.txt`（开头已带追问轮数）
- 想先看提示词不花钱：加 `--dry`
- 建议在 .env 加 `JUDGE_MODEL=`（换个不同模型当裁判，避免自己评自己偏松）

## 3. 录入（不调 API）

到当前项目的评估工作区 `result`（以下命令从项目根目录执行）：

```
cd result
python 自动录入.py
```

自动填成绩单数字列 + 核查表（句子 + AI 初判）：
- B → 填「瞎编核查」「硬信息核查」「白问核查」
- B2 → 填「瞎编核查B2」「硬信息核查B2」；白问不重复登记，与 B 相同

## 4. 人工只剩两件事

1. 三张核查表的终判列（「瞎编核查」「瞎编核查B2」「硬信息核查」「硬信息核查B2」，重点核 AI 标"无"和"错"的行）
2. 核查裁判给的白问次数（裁判对照追问记录和攻略初判过了，你抽查即可；不同意见直接改成绩单里的数）
3. 看板：「A-B对比」——B 比 A 看追问的用处，B2 比 B 看二次检索与终版处理组合的效果

## 环境变量

- `EVAL_HOME`：评估工作区路径，默认当前项目根目录下的 `result`，随项目移动或改名；设置此变量时，以指定目录为准。
- `JUDGE_MODEL / JUDGE_API_KEY / JUDGE_BASE_URL`：裁判用别的模型时设置
- `SIM_USER_MODEL / SIM_USER_API_KEY / SIM_USER_BASE_URL`：模式 B 扮演用户的模型（建议换个模型，避免同一个模型"自问自答"过于默契）

## 注意

- A/B 跑题会为每题创建 MCP 子进程（fetch + filesystem）；B2 只恢复 B 的历史并生成终版，无需再启动 MCP
- 三模式全量会产出60份攻略，另有追问过程、模拟用户和60次裁判等调用；不能把60份攻略当作总模型调用次数。先用 `--tasks T01 --modes B2` 试跑
- 追问轮数自动统计；白问次数由裁判初判、你抽查
- 【修改】B2 在 B 之后增加一次终版模型请求，沿用原会话历史，本次不携带工具定义；输入还包含合并资料及最终输出指令。比 B 多出这次生成和一次二次检索的接口费用，具体额度取决于输入输出长度。
